A field guide to the skill library

Seventeen skills for building, reviewing, and shipping WordPress-plugin work with Claude Code — one orchestrator that sequences them, and sixteen specialists you can call directly.

nkb-bd/ff-team-skills · updated July 2026 · new-feature illustrated manual

Which skill, when

Start from what you want, not from the skill list.

Build a feature or capability$new-feature
Fix a bug someone reported$bug-fix
Hunt for bugs nobody reported yet$bug-fix find
Check a branch before merging$pre-merge-review
Deep quarterly security/perf sweep$plugin-audit
Write the PR description$pr-descriptor
Stress-test a plan against the docs$grill-with-docs
Stress-test a plan, no docs involved$grill-me
Design an API before building it$design-an-interface
Build test-first$tdd
Verify how an API behaves before coding$source-driven-development
Second-guess a high-stakes / irreversible call$doubt-driven-development
Understand unfamiliar code deeply$explain-this
Get un-lost in a code area$zoom-out
Find where the architecture can deepen$improve-codebase-architecture
Onboard agents to a new repo$agents-onboarding
Wire the code graph into a repo$setup-code-review-graph
Rule of thumb: a typo or one-liner needs no skill at all — just commit. Anything bigger that creates code goes through new-feature; anything that judges code goes through pre-merge-review or plugin-audit.

How they chain

The feature pipeline. new-feature decides which specialists to invoke and when; everything below it also works standalone.

issue / PRD / plain words→triage→grill-with-docs→openspec + design-an-interface→spec→tdd→pre-merge-review→pr-descriptor→ship mid-build detours — bug surfaces → bug-fix  ·  lost → zoom-out  ·  unverified API → source-driven-development  ·  irreversible decision → doubt-driven-development  ·  refactor itch → improve-codebase-architecture (after merge, never mid-feature)

Between every stage sits an approval gate: the skill shows you an artifact (problem statement, proposal, spec, review report, PR draft) and waits for your "yes". Pushing and PR-creation additionally require explicit consent every time — once-approved is not forever-approved.

01Orchestrators

Skills that sequence other skills.

new-feature

The end-to-end feature workflow. Six phases — triage → align → plan → spec → build → review → ship — with approval gates between them. Picks an intensity tier first, so a small fix doesn't get big-feature ceremony.

TierLooks likeWhat runs
Trivialtypo, config tweaknothing — just commit
Smallsingle-file fixbuild + light review
Mediumone endpoint, ~3 filesplan + spec + build + light review
Largenew module / serviceeverything, deep review
BreakingAPI / schema changeeverything + post-merge audit
WhenStarting any feature or non-trivial enhancement. Works from an issue #, a PRD, or just your own words — "we need a duplicate-form button" is a valid starting point.
ExampleUse $new-feature — users should be able to export entries as PDF

Full mechanics — every gate, check, and question — in the illustrated manual.

rigorous-coding-workflow

The principles layer underneath new-feature: plan before executing, use subagents to keep context clean, capture lessons from corrections, verify before declaring done, push for elegance.

WhenAny multi-step task that isn't a feature build — refactors, failing CI, re-attempts of work that went sideways. For features, new-feature already applies it.
ExampleUse $rigorous-coding-workflow — migrate the export module to the new queue API

02Plan & align

Get the thinking right before any code exists.

grill-with-docs

An interview that stress-tests your plan against the project's existing domain model — CONTEXT.md terms, ADR decisions — and updates those docs inline as decisions crystallise.

WhenBefore building something that touches established domain language. Also runs automatically as new-feature's align phase.
ExampleUse $grill-with-docs — I want to add "form templates" but we already have "form presets"

grill-me

Pure plan interrogation — resolves every branch of the decision tree until you and the agent share one understanding. No documents touched.

WhenYou have a design in your head and want it stress-tested before committing to it. Lighter than grill-with-docs; no docs needed.
ExampleUse $grill-me on my plan to cache rendered forms per-locale

design-an-interface

Generates three or more radically different designs for a module's interface using parallel sub-agents, each given a divergent constraint (minimize methods / maximize flexibility / optimize the common case). You compare and pick.

WhenBefore building any API or module whose shape isn't obvious. new-feature invokes it automatically for Large-tier work.
ExampleUse $design-an-interface for the new WebhookDispatcher service

03Build

Writing the code, test-first, without getting lost.

tdd

Red-green-refactor with a "correct seam" rule: the failing test must exercise the behavior at the real call site, not a shallower seam that gives false confidence.

WhenBuilding anything testable. new-feature's entire build phase runs through it — one red-green-refactor cycle per spec scenario.
ExampleUse $tdd — the sanitizer should strip script tags but keep allowed HTML

source-driven-development

Grounds every framework claim in an authoritative source before you assert it — the WPFluent / Vidstack / hls.js / Gutenberg / WP-core signature or contract, checked against the vendored source (the version this repo actually ships) or the official docs, never memory. Anything you can't ground gets an explicit UNVERIFIED: tag instead of a silent guess.

WhenWriting code against a library API, or debugging a "the framework should do X" hypothesis. new-feature calls it in the spec phase and before any build step that touches an external API.
ExampleUse $source-driven-development — confirm the vidstack event fires before loadedmetadata

bug-fix

Two modes. Fix (default): reproduce → minimise → hypothesise → instrument → fix → regression-test — the feedback loop comes first, never hypothesize before you can reproduce. Find: a plugin-wide discovery sweep where a Finder proposes bugs, a Verifier confirms them, and only confirmed ones reach the report.

WhenAnything broken, throwing, or behaving strangely. Use find-mode when nobody reported anything but you want to know what's lurking.
ExampleUse $bug-fix — duplicate entries appear when submitting with slow network
ExampleUse $bug-fix find on this plugin

zoom-out

Builds a higher-level map of the code area you're standing in — modules, flows, seams — so you can re-orient instead of wandering file to file.

WhenMid-task, the moment you notice you're reading files without a hypothesis. Also useful before reviewing an unfamiliar subsystem.
ExampleUse $zoom-out on app/Services/Payments

04Review & quality

Judging code — before merge, after merge, and for your own understanding.

pre-merge-review

The canonical branch review. Full mode runs seven parallel detectors — accessibility, async races, UI↔backend wiring, permissions, backwards-compat, error-handling UX, performance & data integrity — plus sequential pattern passes (WP-PHP, JS, Vue, state-machine, adversarial inputs). Writes one re-runnable report; re-running marks fixed findings [cleared].

WhenBefore pushing any branch. Use light for single-file diffs — it skips the parallel detectors.
ExampleUse $pre-merge-review — diff against origin/dev
ExampleUse $pre-merge-review light

doubt-driven-development

Adversarial fresh-context review for the calls that are expensive to reverse. Runs a CLAIM → EXTRACT → DOUBT → RECONCILE → STOP loop: state the decision as one falsifiable sentence, list its load-bearing assumptions, then spawn a clean-context skeptic whose only job is to refute them. Surviving doubts are resolved or explicitly accepted before an explicit go / no-go.

WhenBefore a schema migration, a public hook-contract change, a capability change, deleting code you didn't write, or any security-sensitive call. new-feature invokes it at the Breaking-tier spec gate, inside /build auto, and on non-trivial review fixes. Skip for reversible, low-blast-radius edits.
ExampleUse $doubt-driven-development — is renaming this filter's third arg safe for shipped addons?

plugin-audit

A deep, evidence-driven audit of a whole plugin: security (severity-ranked), optimization, dead code, and end-to-end UI-to-database traceability. Produces a remediation backlog, not vibes.

WhenQuarterly, after Breaking-tier merges, or when inheriting a codebase you don't trust yet.
ExampleUse $plugin-audit and produce plugin-audit.md

improve-codebase-architecture

Finds deepening opportunities — modules to consolidate, seams to strengthen, testability gaps — guided by the domain language in CONTEXT.md and the decisions in ADRs.

WhenAfter merge, when an area felt architecturally wrong mid-feature. Never mid-feature: new-feature explicitly defers refactor itches here.
ExampleUse $improve-codebase-architecture on the Transfer module

explain-this

Teaches you a file, feature, or PR until you actually own it. Starts teaching immediately — no "what do you already know?" interrogation — walking the material stage by stage with a running coverage checklist, drilling the why behind every decision (eli5 / eli14 / intern depth on request). Quizzes only if you ask.

WhenOnboarding to a subsystem, studying a teammate's change before reviewing it, or any "I need to own this area" moment. For a quick "what does this line do", just ask normally.
ExampleUse $explain-this on the submission validation pipeline

05Ship & setup

Getting work out the door, and getting repos ready for agents.

pr-descriptor

Drafts a concise, why-first PR description from the actual git diff, filling the repo's PR template (or its bundled default). Includes the Closes #n reference when an issue is in play.

WhenEvery PR. new-feature calls it automatically at ship time.
ExampleUse $pr-descriptor for the current branch

agents-onboarding

Creates or refreshes a repository's AGENTS.md with high-signal onboarding guidance — architecture depth, local validation workflow, the things agents keep getting wrong without it.

WhenNew repo, or when agent behavior on a repo varies more than it should.
ExampleUse $agents-onboarding to create AGENTS.md for this repo

setup-code-review-graph

Wires the code-review-graph MCP server into a repo: project-scoped .mcp.json, CLAUDE.md instructions block, gitignore line, seed graph build. After this, agents query callers/dependents/test-coverage structurally instead of grepping.

WhenOnboarding any repo you'll work in regularly. One-time per repo.
ExampleUse $setup-code-review-graph on this repo

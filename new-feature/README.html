01

How it works — the phase rail

Seven stations, six stops. Between phases sit alignment gates (show artifact, wait for "yes") and consent gates (outward-facing actions: push, PR). Gates are where course corrections happen cheaply — a wrong noun costs one sentence at the gate, a rewrite after build.

0

Triage

always

Start-of-run hygiene: archive any merged openspec changes. Read CLAUDE.md / AGENTS.md (they override skill defaults — stack, hook prefix, commit format). Ask what we're building — an upstream artifact (issue #, PRD, openspec change) or a plain-language description; both are first-class answers. Pick a tier; announce it with reasoning. The tier must survive the evidence — detect_changes on the diff can veto a self-declared "Small".

Gate "I picked tier X because Y — agree?" Recalibrate before moving on.
1

Align

tier ≥ medium · mandatory ≥ large

Interview until shared vocabulary: the single canonical noun, the problem + who hits it, the smallest valuable version, constraints from CONTEXT.md/ADRs. Updates CONTEXT.md inline as terms resolve. With an upstream issue, this is a confirmation pass — not re-discovery.

$grill-with-docs
Gate One-sentence problem statement + canonical noun. Wait for "yes".
2

Plan

tier ≥ medium

Input: the canonical noun (from the grill, the artifact title, or ask the user — never improvised). Name the change issue-<n>-<noun> for a two-way tracker link. Scaffold with openspec, write proposal.md (why / what changes / capabilities / impact). Tier ≥ Large: generate 3+ radically different interface designs in parallel and pick one.

openspec new change$design-an-interface (≥ large)
Gate proposal.md (+ chosen design). Wait for "yes". May batch with Phase 3's gate when solo.
3

Spec

tier ≥ medium

WHEN/THEN scenarios in spec.md — every scenario is a future test. design.md records decisions with alternatives + rationale. tasks.md holds checkbox milestones small enough for one session. Must pass openspec validate --strict.

openspec validate --strict
Gate spec + tasks. Wait for "yes".
4

Build

always

Red-green-refactor per scenario, test at the correct seam. Full WordPress security checklist on every handler (see checks board). Commit per milestone with prefix format. New PHP class → composer dump-autoload + classmap grep. Bug mid-build → reproduce before hypothesising. Architecture itch → defer post-merge, don't refactor the world mid-feature.

$tdd$simplify (if available)$bug-fix (if bug surfaces)$zoom-out (if lost · if available)
Consent Never git push without explicit consent — once-approved is not forever-approved.
5

Review

always · light ≤ medium · deep ≥ large

Light: sequential pattern passes only (WP-PHP, JS, Vue, backwards-compat, adversarial inputs). Deep: seven parallel detectors — accessibility, async races, UI↔backend wiring, permissions, backwards-compat, error-handling UX, performance + data integrity — plus the sequential passes. Re-runnable report; resolved findings marked [cleared]. Every Blocking addressed before push.

$pre-merge-review [light]detect_changes / get_review_context
Gate Show the report. Wait for "yes" before pushing.
6

Ship

always

Draft the PR description from the actual git diff; include Closes #<n> / Fixes #<n> so the upstream issue auto-closes on merge. After merge: openspec archive (Phase 0's hygiene check is the backstop if this session is gone by then) and verify the issue closed.

$pr-descriptoropenspec archive
Consent Show the draft, then ask before gh pr create. Never automatic, never inherited.

Tier matrix — what actually runs

Phase 0 classifies the request; the tier decides coverage. Each tier adds phases going down — Medium is the first tier that plans, Large the first that grills and specs formally.

TierSignal P1 AlignP2 PlanP3 Spec P4 BuildP5 ReviewP6 Ship Extras
Trivial Typo, config tweak, single-line copy — skill exits entirely · just commit —
Small Single-file fix, one-component cosmetic change —
Medium One Vue panel, one endpoint, bugfix touching ~3 files —
Large New module / service / policy / capability / data migration design-an-interface
Breaking API change, schema migration, removed feature + plugin-audit post-merge
runs review · light review · deep optional (noun must still be resolved) skipped
Evidence veto: the tier must survive the diff. Breaking signals — schema change, removed hook, changed REST signature — escalate the tier even if the request sounded Small. Self-declared tiers don't override what detect_changes says.

04

The checks it runs

Four boards: WordPress security on every handler, code-quality on every refactor, process verifications at phase boundaries, and the consent rules that never relax.

WordPress security

Phase 4 · every handler · do not skip
  • Every $_GET/$_POST/$_REQUEST sanitized with the right sanitizer + wp_unslash()
  • Every output escaped at the point of output — esc_html / esc_attr / esc_url / esc_js
  • Every REST route has a policy class or explicit permission_callback
  • All $wpdb calls with variables use prepare()
  • Nonce verified before capability check on every AJAX/REST handler
  • current_user_can() on every data-modifying endpoint
  • Hook names use the plugin prefix; filters/actions exposed at meaningful seams for pro addons
Never  permission_callback => '__return_true'

Code quality

Phase 4 · refactor step · after green only
  • Boring, obvious code first — three similar lines beat a premature abstraction
  • Short functions, intention-revealing names; no helper layers that exist to be helpers
  • No comments restating code — only the non-obvious why (hidden constraint, invariant, workaround)
  • Match the surrounding style — existing patterns before inventing new ones
  • No half-done implementations or flags for code not yet written
  • Vue style follows the target repo — FluentForm = Vue 2 Options API, FluentPlayer = Vue 3 <script setup>

Process verifications

Phase boundaries · mechanical, not vibes
  • P0: archive-hygiene sweep of openspec/changes/ for already-merged work
  • P0: tier vs. evidence — detect_changes risk score can escalate the tier
  • P3: openspec validate --strict must pass before the gate
  • P4: new PHP class → composer dump-autoload, then grep autoload_classmap.php — classmap-authoritative builds hide new classes
  • P5: every Blocking finding addressed before push; re-run marks fixes [cleared]
  • P6: PR carries Closes #n / Fixes #n; verify auto-close after merge

Consent rules

Outward-facing actions · stated at both sites
  • Local commits flow freely — one per milestone, prefix format, no attribution trailers
  • git push requires explicit consent, every time
  • gh pr create requires explicit consent, every time — draft shown first
  • Gate batching allowed only for P2+P3 when solo; alignment, pre-push and PR gates always stand alone
Rule  Once-approved is not forever-approved.

Every question it asks you

Two species: alignment gates freeze decisions while they're still one paragraph; consent asks guard outward-facing actions. It never asks permission for reversible, in-workspace work.

Q1Phase 0"What are we working on? An issue #, PRD, or openspec change is great — or just describe the feature or bug in your own words."Artifact → grill becomes confirmation, issue # feeds Closes #n. Plain description → restated back in one sentence, Phase 1 does first-pass discovery. Sounds like a bug → offers $bug-fix instead. Never bounces you to go file an issue first.
